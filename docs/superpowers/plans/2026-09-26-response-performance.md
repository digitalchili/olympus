# Response Performance Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Use one sequential implementer and the shared handoff order. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reduce avoidable Olympus delay, prioritizing Michael's confirmed symptom: waiting for the first response after Send.

**Architecture:** Measure admission, worker setup, native execution and display separately. Keep the Hermes execution path, make optional model discovery nonblocking, and remove unused repository diagnostics and overlapping evidence reads. Preserve exact pre-agent source identity, recovery admission and existing frame-batched streaming.

**Tech Stack:** Existing TypeScript/Express, Python/Hermes, React, Git CLI and disposable test/browser fixtures; no telemetry service or new runtime dependency.

**Spec:** [Shared design](../specs/2026-09-26-reliability-improvements-design.md), especially Global constraints and P. Entry point: [handoff and task ledger](2026-09-26-reliability-handoff.md).

## Global Constraints

All twelve shared Global constraints apply. Diagnostics are opt-in, local and metadata-only. Do not bypass ownership/background-work probes, move the baseline after agent execution, cache source freshness by HEAD/mtime/TTL, change the selected model/reasoning, raise concurrency, or add execution timeouts to make results appear faster. Do not read or operate another Hermes installation for a comparison.

## Review Focus

- Optional model discovery stalls while a user sends or stops a task: P2 plus R1.
- Old task/profile settings complete after switching or after an explicit selection: P2.
- Files change with identical HEAD, size or mtime; symlinks/deletions remain significant: P3.
- A slow evidence response overlaps polling or updates a different task after navigation: P3.
- Cold startup, first thinking, first answer and verification completion get confused: P1/P4.

## Task P1: Safe stage timings and a reproducible latency baseline

**Files:** Create `server/performance-timing.ts`, `server/workers/hermes_performance.py`, `tests/performance_timing.test.ts`, `tests/test_worker_performance.py`, `qa/response-performance-2026-09-26.md`. Use existing fixture patterns in `tests/fixtures/task-start-ui-server.ts` and `tests/reconnect_chat.test.ts`; add a dedicated disposable `tests/fixtures/response-performance-server.ts` if the existing fixture cannot cover the timings without becoming complex. Ensure the existing asset-copy script includes the new Python helper.

**Interfaces:**

- `createPerformanceTrace(): PerformanceTrace | null` returns null unless `OLYMPUS_PERF_DIAGNOSTICS=1`. A trace has a generated opaque `id`, `bindRun(runId: string): void`, `mark(stage: PerformanceStage): void`, `span<T>(stage: PerformanceStage, work: () => Promise<T>): Promise<T>`, and `finish(outcome: 'done' | 'error' | 'stopped' | 'rejected'): void`. `PerformanceStage` is `'inventory' | 'workspace' | 'accepted' | 'baseline' | 'adapter_dispatch' | 'first_activity' | 'first_text' | 'native_done' | 'verification' | 'artifacts'`. Use `performance.now()` for durations. Logs use `[olympus-perf]` plus a bounded JSON record, no new DB table/API endpoint.
- Create the per-send trace in the existing task-recovery message middleware, before `getBackgroundWork`, and carry it in `res.locals.performanceTrace` through Project preparation and chat admission. Direct-router test fixtures may create a fallback at chat entry. After 202, finish the trace with the background run's settlement, not HTTP response close. Log the server-owned accepted run ID once for correlation. Rejected admission finishes separately and never invents a run.
- Add optional `timingTraceId?: string` to internal `AgentRunOptions` and the `chat` WorkerRequest; `buildChatWorkerRequest` propagates it. Never take it from the HTTP request body. Native helper `PerformanceTrace(trace_id: str | None)` supports `mark(stage: str)` and `finish(outcome: str)` with `time.monotonic()` and stderr output only. Its stage allowlist is `dispatched`, `slot_acquired`, `history_ready`, `mcp_ready`, `runtime_ready`, `agent_ready`, `native_started`, `first_activity`, `first_text`, `cleaned_up`; outcome uses the Node allowlist. Thread the optional trace through `_run_chat` and `_create_agent` via a defaulted `performance_trace` parameter, not process-global mutable state. Enable it only when the same diagnostics environment flag is set. Never print timing lines into JSONL stdout.
- Browser receive/paint timing belongs to the local benchmark fixture/browser runner. No permanent client telemetry, third-party export, production debug endpoint or transcript logging.

With a fake monotonic clock, an inventory span of 40ms, baseline of 80ms and first-text mark of 150ms report those distinct values; duplicate first marks are ignored; finish is idempotent on success/error/Stop. Inject token/message/path sentinels into adjacent fake objects and verify no sentinel appears in captured logs. Missing stages stay absent, never zero. Stage logging failure must not fail a task.
