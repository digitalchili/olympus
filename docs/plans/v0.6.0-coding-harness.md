# v0.6.0 coding harness implementation plan

**Goal:** Deliver the six reviewed reliability repairs and a coding workflow with durable Git/test evidence, keeping Hermes as the runtime.

**Architecture:** Hermes owns transcripts, tools and child execution. Olympus owns task/run lifecycle, bounded recovery, Git ownership and verification evidence. Reuse existing SQLite, worker JSONL, project editor and chat components. No runtime rewrite or second transcript database.

**Authorization:** User approved the preceding review's six fixes and earlier coding-harness recommendations, and requested v0.6.0. Implement and verify locally in the release worktree. Publishing and updating a live installation are separate operations.

## Global constraints

- Keep changes simple, profile/task scoped and compatible with existing local installations.
- Preserve user files, credentials, existing sessions and unrelated background work.
- Never replay the original request because a delivery claim is unavailable.
- User stop and pending approval are never automatic-resume instructions.
- All execution phases share an absolute deadline; recovery has a finite attempt/time budget.
- Review promotion for coding changes requires saved passing verification for the same working tree; ordinary noncoding tasks retain their existing flow.
- No claim that a checkpoint exists without a recorded receipt.
- No live profile or deployment mutations during verification.

### Task 1: Worker result reconciliation and checkpoint receipt

Files: `server/workers/hermes_worker.py`, focused new Python recovery module, `server/workers/hermes_background_work.py`, Python regression tests.

Implement durable task-scoped pending-delegation/result bookkeeping. Verify the pinned Hermes source APIs before relying on native state. Queue notifications are hints: reconcile missing notifications with native completed results. Persist pending/result state before delivery, retain failed/interrupted synthesis as unfinished, and do not rerun the previous user request on failed claims. Bound waits and expose waiting progress. Checkpoint receipts describe actual saved recovery state, never an assumed model-created checkpoint. Plain human cancellation blocks automatic recovery. Keep compatibility behavior explicit when native recovery is unavailable.

Produces: background inventory retains `{available, work}` and may add `continuation: {status: 'pending' | 'blocked' | 'none', reason?: string}`. Normal fresh chat reads pending journal state and injects undelivered result context without replaying the original request. Status `pending` means safely recoverable journal state. Root owns TS schema and automatic-recovery scheduler integration.

- [ ] Convert claim-busy, interrupted synthesis, incomplete synthesis and missing-notification probes into failing regression tests.
- [ ] Implement minimal durable bookkeeping and native reconciliation; verify restart, duplicate-event and wrong-task isolation.
- [ ] Run Python regression suites; document native API revision and limitations.

### Task 3: Durable bounded continuation and reconnect

Files: focused recovery DB/service modules, `server/index.ts`, chat/recovery routes, `client/src/hooks/useChat.ts`, failure presentation and tests.

- [ ] Persist automatic recovery metadata keyed by exact failed run, separate from the user's queued follow-up.

- [ ] At most two automatic recovery attempts within two hours of the original run start. Preserve original settings and task ownership; stop on explicit human stop, approval, terminal success, or exhausted budget.
- [ ] Refresh persisted history/status on reconnect even without a live snapshot; expose reconnecting state.
- [ ] Replace unsupported checkpoint copy with factual status and real receipt evidence when available.

## Design rulings

- The earlier worktree comparison identified a tradeoff, not a requirement to discard the repository's single-editor rule. This release keeps safe dedicated project checkouts and adds evidence to that workflow.
- No universal superiority or flawless-runtime guarantee can be established by source changes. Acceptance is the concrete failure/recovery and verified-coding behavior above.
- Native checkpoints are optional. An Olympus recovery receipt establishes saved continuation metadata, not a backup of arbitrary files or proof of completed work.
