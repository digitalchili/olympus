# Composer draft updates (v0.7.45)

- Reproduced draft and staged-attachment loss when the same conversation rehydrates after a chat callback changes. The history-loading effect previously reset user-owned composer state as well as server state. Queue arrival by itself did not reproduce text loss; the exact triggering sequence in the reported production browser was not observed.
- Draft reset now belongs to conversation/profile changes. History/queue refreshes cannot clear text, staged attachments, or selected collaborators. Existing send/rejection revision protection remains.
- Saved GitHub publication appears above the composer as “Push requested”, separate from the next message. Normal queued messages retain their editing/steering controls. Publication admission, checks, cancellation, and server queue semantics are unchanged.
- Regression: `tests/task_chat_draft_updates.test.ts` failed with empty text before the fix and passes afterward. It covers queue arrival, history refresh, attachment retention, publication completion, task/profile changes, and absence of message submissions. Existing attachment and reconnect regressions pass.
- The full local test run reached an assertion for the old publication label. After updating that assertion, the affected test and every remaining test passed; all earlier tests had already passed. Typecheck and production build passed with Node 22.22.3.
- Browser check used the actual TaskChat component with disposable HTTP/SSE responses. Typed a new message, showed the pending publication, added more text, advanced to publishing, then completed it. Text stayed intact, the status appeared outside the composer, and Send became available after completion. No production task, model call, or Git push was triggered by the fixture.
